# Sentinel

항공 엔진 **예지보전** 웹 대시보드입니다. 정비 계획 담당자가 엔진 플릿의 남은 수명 예측을 보고, 어떤 엔진을 언제까지 정비 요청해야 하는지 판단하고, 처리 상태를 기록합니다.

> 화면의 데이터는 **시연용**입니다. NASA C-MAPSS FD004 터보팬 열화 시뮬레이션이며 실제 항공기 데이터가 아닙니다.
> 팀 "5조 감시자들"의 프로젝트 결과물이고, 분석 과정과 평가는 분석 저장소에 있습니다: [`5_Sentinel_python`](https://github.com/posco-knda/5_Sentinel_python)

## 화면

| 화면 | 담당자가 하는 일 |
|---|---|
| **현황** `/` | 오늘 조치가 필요한 엔진 수, **정비 일정 달력**(날짜별 요청 기한·승인된 정비·결재 대기), 정비 요청이 도래하는 주별 수요, 예측 남은 수명 분포, 점검이 예상되는 모듈 |
| **정비 계획** `/plan` | 정비 요청 기한이 급한 순으로 엔진을 보고 검토 → 결재 요청 → (승인 뒤) 정비 완료로 처리 |
| **결재함** `/approvals` | 담당자가 올린 정비 요청을 운영 책임자가 검증해 승인·반려. 담당자는 진행 상태와 반려 사유를 확인 |
| **알림** `/alerts` | 위험·주의 구간에 들어온 알림을 최근 순으로 보고 확인 처리 |
| **엔진** `/equipment` | 플릿의 모든 엔진 목록. 등급 필터, 정렬(요청 기한·남은 수명·번호), 번호 검색, 쪽 나누기. 행을 누르면 엔진 상세로 이동 |
| **엔진 상세** `/equipment/engine-103` | 개요(남은 수명·예측 구간·권고) · 고장 진단(센서 → 점검 모듈 → 경보 시점 → 권고) · 센서 · 이력, 진단 리포트 |
| **엔진 리포트** `/report/:id` | 결론 한 줄, 요약(AI 요약 선택), 핵심 수치, 추이, 점검 예상 모듈, **결재 이력과 확인란(AI 작성·담당자·책임자)**을 A4로 인쇄·PDF 저장. Slack 알림 |
| **주간 리포트** `/weekly` | 최근 7일 결재 현황, 정비 요청 도래(주별), 점검 예상 모듈(부품·인력 준비용), 우선 정비 대상 10대, 결재 이력을 한 장으로 요약. AI 요약·PDF 저장 |
| **비용 분석** `/cost` | 사후 정비와 예지 정비의 비용을 단가를 바꿔 가며 비교 (가정값 기반) |
| **설정** `/settings` | 화면 테마(라이트·다크·시스템 설정), 알림 민감도, 하루 비행 횟수, 정비 준비 기간, 자동 알림, 연동 상태, 처리 기록 관리 |

- 남은 수명은 **cycle(비행 1회)** 단위이고, 설정의 "하루 비행 횟수"로 일로 바꿉니다.
- **정비 요청 기한 = 예측 남은 수명(일) − 정비 준비 기간.** 0 이하이면 "기한 지남"입니다.
- 위험은 예측 남은 수명 ≤ 알림 민감도(기본 40 cycle), 주의는 < 80입니다. 설정을 바꾸면 모든 화면이 다시 계산됩니다.
- **사람이 두 번 판단합니다(human-in-the-loop).** AI가 정리한 권고를 정비 담당자가 검토해 사유와 함께 결재를 올리고, 운영 책임자가 필요한 정비인지 검증해 승인하거나 반려합니다. 승인된 건만 정비 예정이 되고, 모든 단계는 누가·언제·왜 했는지 엔진의 이력에 남습니다.
- 로그인은 **시연용**입니다. 계정은 `src/lib/accounts.ts`에 있고(정비 담당자, 운영 책임자) 로그인 화면의 버튼으로 입력할 수 있습니다. 로그인은 탭마다 따로라서, 탭 두 개에 다른 계정으로 들어가면 결재가 오가는 모습이 바로 반영됩니다. 실제 인증이 아니며 서비스에서는 서버 인증이 필요합니다.
- 처리 기록과 설정은 이 브라우저(`localStorage`)에 저장됩니다. 서버·DB는 없어서 다른 기기와는 공유되지 않습니다(같은 브라우저의 탭끼리만 공유).
- **정비 일정 규칙(주간 계획)**: 희망 정비일·확정 정비일에는 아래 규칙이 적용됩니다. 결재 창에서 사유와 함께 막고, 승인할 때 한 번 더 검사합니다(`src/lib/schedule.ts`, `npm run test:logic`).
  1. 이번 주와 지난 날짜에는 정비를 새로 잡을 수 없습니다 → 다음 주 월요일부터
  2. 정비 준비 기간(설정, 기본 7일)이 지난 뒤여야 합니다
  3. 정비는 평일(월~금)에만 합니다
  4. 하루에 정비할 수 있는 엔진 수(설정, 기본 4대)가 있어서, 이미 정비 예정(승인)이 가득 찬 날은 예약할 수 없습니다. 결재 대기 건은 자리를 차지하지 않고 승인 시점에 자리를 확인합니다.
  결재 창은 가능한 날짜와 남은 자리를 추천하고, 현황의 정비 일정 달력은 만석인 날과 정비 가능 자리를 보여 줍니다.
- 현장에서는 정답(실제 남은 수명)을 알 수 없으므로 화면은 예측값과 센서 변화만 씁니다.
- 점검 예상 모듈은 센서가 **가장 크게 변한 모듈을 추정**한 것이며 고장 원인을 확정하지 않습니다.

## 실행

```bash
npm install
npm run dev        # 개발 서버
npm run build      # 정적 빌드 (dist/)
npm run lint
npm run test:api   # 서버 함수 검증 (Node 22.18+ / 24)
npm run test:logic # 정비 일정 규칙 검증
```

## 데이터 갱신

`src/data/` 의 파일은 모두 분석 저장소가 만드는 **자동 생성 파일**이라 직접 고치지 않습니다. 분석 저장소에서 스크립트를 다시 돌려 복사하세요.

| 대시보드 파일 | 분석 저장소 스크립트 | 내용 |
|---|---|---|
| `mock.ts` | `08_export_dashboard_ts.py` | 비용 시뮬레이션 계수, 데이터 정보 |
| `detectionLog.ts` | `18_export_detection_log.py` | 엔진 248대의 마지막 예측 |
| `detectionCurves.ts` | `18_export_detection_log.py` | 경보가 난 엔진의 예측 곡선 (지연 로딩) |
| `partFlowMeta.ts`, `partFlow.ts` | `20_export_part_flow.py` | 센서 이탈도, 모듈 요약 (`partFlow.ts`는 지연 로딩) |
| `uncertainty.ts` | `21_export_uncertainty.py` | 엔진별 90% 예측 구간·생존곡선 |
| `analysisExtras.ts` | `19_export_analysis_extras.py` | 설정 화면의 민감도별 기대 효과 |

```bash
# 분석 저장소(5_Sentinel_python)에서
python scripts/08_export_dashboard_ts.py && python scripts/18_export_detection_log.py \
  && python scripts/19_export_analysis_extras.py && python scripts/20_export_part_flow.py && python scripts/21_export_uncertainty.py
# outputs/FD004/dashboard_data/ 의 파일을 src/data/ 로 복사 (mock.ts, detection_log.ts → detectionLog.ts, detection_curves.ts → detectionCurves.ts,
# part_flow_meta.ts → partFlowMeta.ts, part_flow.ts → partFlow.ts, uncertainty.ts, analysis_extras.ts → analysisExtras.ts)
```

## 배포 (Vercel)

정적 화면과 서버리스 함수(`api/`)를 한 곳에서 배포합니다. `vercel.json`이 새로고침해도 404가 나지 않도록 경로를 `index.html`로 돌립니다(`/api` 제외).

서버 기능은 **환경변수가 있을 때만** 동작하고, 없으면 화면이 "미연결"로 안내합니다. 값은 서버에만 있고 브라우저로 나가지 않습니다.

| 함수 | 환경변수 | 하는 일 |
|---|---|---|
| `api/notify.ts` | `SLACK_WEBHOOK_URL` | Slack 채널로 알림 전송 (Incoming Webhook): 엔진 진단(수동), 결재 이벤트(자동), 신규 즉시 조치(자동) |
| `api/summary.ts` | `GEMINI_API_KEY`(무료 한도 있음, 선택: `GEMINI_MODEL`) 또는 `ANTHROPIC_API_KEY`(선택: `ANTHROPIC_MODEL`) | 엔진 진단 요약, 주간 리포트 요약(`kind: 'weekly'`)을 생성형 AI로 작성. 둘 다 있으면 Gemini 사용 |
| `api/status.ts` | — | 위 두 가지가 설정돼 있는지만 true/false로 알림 (설정 화면이 사용) |

### 자동 알림
Slack이 연결돼 있으면 사람이 버튼을 누르지 않아도 알림이 갑니다(설정 › 자동 알림에서 각각 끌 수 있음).

| 상황 | 메시지 |
|---|---|
| 정비 담당자가 결재를 올림 | `결재 요청 · Engine #31` — 요청자, 희망 정비일, 판단 사유, 결재함 링크 |
| 운영 책임자가 승인·반려 | `승인`/`반려 · Engine #31` — 승인자, 정비일 또는 반려 사유, 엔진 이력 링크 |
| 정비 완료 처리 | `정비 완료 · Engine #31` |
| 엔진이 새로 '즉시 조치'가 됨 | `신규 즉시 조치 N대` — 상위 8대 목록과 나머지 대수 |

신규 즉시 조치는 화면이 열려 있는 브라우저가 감지합니다. 처음 열 때는 지금 상태를 기준선으로만 기록하고 알리지 않으며, 이후 설정(하루 비행 횟수·민감도·정비 준비 기간)이나 예측이 바뀌어 **새로 즉시 조치가 된 엔진만** 한 건으로 묶어 보냅니다. 이미 알린 엔진은 다시 보내지 않고(같은 브라우저의 다른 탭 포함), 즉시 조치에서 벗어난 엔진은 다시 나빠지면 새로 알립니다. 서버가 상시 돌지 않는 구조라서 실제 서비스에서는 예측이 갱신될 때 서버 작업이 이 검사를 대신합니다.

**개발 서버에서 직접 써 보기**: `.env.example`을 `.env.local`로 복사해 `GEMINI_API_KEY`(와 `SLACK_WEBHOOK_URL`)를 채우고 `npm run dev`를 다시 실행하면, 개발 서버가 `api/*.ts`를 배포 때와 같은 코드로 돌립니다. `.env.local`은 git에 올라가지 않습니다. 키는 서버 쪽에서만 쓰이고 브라우저로 나가지 않으며, 주간 리포트에는 집계 숫자와 반려 사유(100자 이내)만 AI로 보냅니다. **Gemini 무료 한도에서는 입력이 Google의 서비스 개선에 쓰일 수 있으므로**, 시연 데이터가 아닌 실제 운항·정비 정보는 보내지 마세요.

`npm run test:api`가 모의 요청으로 입력 검증, Slack 멘션 이스케이프, 오류 처리, 비밀값 비노출을 키 없이 검증합니다. 실제 키로 외부 서비스를 호출하는 확인은 배포 후에 필요합니다.

## 기술 스택

Vite · React · TypeScript · Tailwind v4 · Recharts · Framer Motion. 화면은 처음 열 때 불러오고(코드 분할), 큰 데이터(`partFlow` 346KB, `detectionCurves` 207KB)는 필요한 화면에서만 불러옵니다.
