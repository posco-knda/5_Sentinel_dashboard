## 1. 왜 코드까지 같이 고쳤는가

처음에는 "새 파이프라인 결과를 기존 대시보드가 읽을 수 있는 모양으로만 바꾸면 되지
않을까" 생각했지만, 실제로 비교해보니 **개념 자체가 달라서** 데이터 모양만 맞추는
것으로는 부족했습니다.

| | 기존 (TCM/냉간압연) | 신규 (C-MAPSS/터보팬) |
|---|---|---|
| 감시 대상 | 5단 텐덤 라인의 스탠드(Stand) | 엔진(Engine) — 100대가 서로 독립 |
| 시간축 | 코일(coil) 생산 순서, 전체 라인이 같은 시계열 공유 | 사이클(cycle) 가동 순서, **엔진마다 자기만의 시간축** |
| 예측 대상 | 작업롤 잔존 마일리지(km) | 잔존수명 RUL(cycle) |
| "이상"의 정의 | RandomForest 이상탐지 분류기의 이진 출력 | 회귀로 예측한 RUL이 위험 기준(30cycle) 이하로 내려간 상태 (§11) |
| 고장 유형 | 전동기/베어링/작업롤/압하 4종 | 터보팬 열화 1종(EngineRemoval) |
| 설비 상세 화면 | Stand 3 하나로 고정 | 9개 엔진 중 아무거나 선택해서 봄(라우트 파라미터로 동적 전환) |

그래서 "데이터 형태를 고치거나, 대시보드 형태를 고치거나" 둘 중 하나가 아니라
**둘 다** 손을 댔습니다. 데이터만 새로 채우면 화면 문구가 계속 "스탠드/코일/압연력"이라고
말하는데 실제로는 "엔진/사이클/RUL"을 보여주는 모순이 생기고, 코드만 고치고 기존
가짜 데이터를 그대로 쓰면 담당자 발표 자료로 쓸 수 없었기 때문입니다.

## 3. "정비 우선순위" 랭킹을 왜 고정된 스냅샷으로 만들었는가

기존 대시보드는 5개 스탠드가 **같은 생산 라인의 같은 시계열**을 공유한다고 가정하고,
스크러버(시간 슬라이더)를 움직이면 모든 스탠드의 헬스 점수가 같은 "코일 순번" 기준으로
같이 바뀌도록 설계돼 있었습니다.

C-MAPSS는 엔진 100대가 **서로 완전히 독립적인 자기만의 수명 시계열**을 가집니다(엔진마다
관측 시작 시점, 길이가 전부 다름). "전체 엔진 공통의 시각 t"라는 개념 자체가 존재하지
않기 때문에, 원래 구조를 그대로 억지로 끼워 맞추면 없는 데이터를 지어내야 했습니다.

그래서 두 가지로 나눠서 처리했습니다.
- **랭킹 카드(9개 엔진 비교)**: 각 엔진의 **마지막 관측 시점 기준** 헬스 점수로 고정.
  스크러버를 움직여도 값이 바뀌지 않습니다 (`getEquipmentRankingAtHour()` 코드 주석에
  이유를 남겨뒀습니다).
- **메인 차트·이상탐지 로그·Toast 알림**: 대표 엔진 1대(#37)로 범위를 좁혀서, 그 엔진의
  마지막 25사이클 안에서만 스크러버가 의미를 가지도록 함.

**대표 엔진(#37) 고른 기준**: RED 등급인 엔진들 중, 보이는 25포인트 창 **안에서**
GREEN→YELLOW→RED 두 번의 임계값 교차가 모두 일어나는 엔진. 처음(RED<20 기준)에는 37·41·61이
해당해 첫 번째인 37을 골랐고, 위험 기준을 30으로 바꾼 뒤에도 37이 조건을 만족해 발표 자료와의
일관성을 위해 그대로 고정했습니다 (생성 스크립트가 조건을 매번 검사합니다).

## 4. "위험 조기경보" 성능 지표를 다시 계산한 이유

기존 대시보드의 RandomForest 분류기 성능(precision 0.979 / recall 1.0 / F1 0.989)은
거의 완벽에 가까운 숫자였는데, 이는 원래 사용하던 시뮬레이션 데이터가 실제 현장보다
이상 패턴이 훨씬 뚜렷했기 때문입니다.

C-MAPSS FD001에는 "위험"이라는 이진 라벨이 원래 없습니다. 대신, **LSTM이 회귀로 예측한
RUL 값**을 그대로 쓰는 것이 이 프로젝트의 핵심입니다. 그래서 "RUL 예측값이 30cycle
이하면 위험"이라는 규칙을 세우고, test 엔진 100대의 마지막 관측 시점에 대한 실제 예측값과
실제 정답을 비교해서 confusion matrix(TP=24, FN=1, FP=1)를 직접 계산했습니다 — precision
0.96 / recall 0.96 / F1 0.96. (처음 20cycle 기준일 때는 TP=11, FN=2, FP=4로 0.73/0.85/0.79였습니다.)
엔진당 한 시점만 보는 평가라 표본이 적으므로, 모든 운행 시점을 보는 더 엄격한 평가는 분석 레포의
`09_classification.py`(과제 필수 과제, validation F1 0.90) 결과를 함께 보세요.

이 방식은 "회귀 예측값을 임계값으로 잘라서 분류 문제처럼 평가할 수도 있다"는 아이디어를
그대로 구현한 것입니다.

## 5. 정비 이력이 비어있는 이유

C-MAPSS FD001은 엔진 1대당 **정상 가동 시작부터 고장까지 딱 한 번**만 기록한
run-to-failure 데이터입니다. 기존 냉간압연 주제처럼 "작업롤을 여러 번 교체하며 마일리지가
반복적으로 리셋되는" 이력 자체가 데이터에 없습니다. 그래서 이 화면은 가짜로 이력을
지어내는 대신, 왜 이력이 없는지 설명하고 **현재 예측 기반의 향후 권고 1건**만 보여주도록
바꿨습니다.

## 6. 비용 시뮬레이션 값 근거

터보팬 엔진은 고장 유형이 하나(엔진을 내려서 정비)뿐이라, 기존의 전동기/베어링/작업롤/
압하 4유형 비용 모델을 `EngineRemoval` 1유형으로 단순화했습니다. `costModel.types`
안의 숫자는 두 종류로 나뉩니다.

- **실제 결과(가정과 무관)**: `episodes`(25) / `detected`(24) / `missed`(1) /
  `falseAlarms`(1) — 전부 §4의 confusion matrix에서 그대로 가져온 값입니다.
- **가정값(illustrative)**: `hoursPlanned`(4h) / `hoursUnplanned`(24h) /
  `repairPlanned`(800만원) / `repairUnplannedRatio`(3배) 등 — C-MAPSS 데이터에는 비용·
  정비 시간 정보가 전혀 없어서, 항공기 엔진 정비 맥락에서 상식적으로 가정한 값입니다.
  실제 항공사/현장 데이터를 구하면 `scripts/08_export_dashboard_ts.py`의 `COST_ASSUMPTIONS`
  값만 바꿔서 다시 생성하면 됩니다.

시뮬레이션 화면(`Simulation.tsx`)의 슬라이더 재계산 로직(`computeScenario()`)은
파이썬 쪽 `compute_scenario()`와 완전히 동일한 수식입니다 — 유형이 하나뿐이라 원래
있던 "유형별 합산" 구조를 그대로 남겨둬도 정확히 동작하고, 나중에 유형이 늘어나도 코드를
고칠 필요가 없습니다.

## 9. RUL 90% 구간 · 생존곡선 계산 수정 (2026-09-29)

처음 연동(2026-09-28) 때 값을 파이썬 결과와 다시 대조해보니 두 가지 문제가 있었습니다.

1. **신뢰구간의 위/아래가 뒤집혀 있었음.** 예전 값은 `[예측 − 18.6, 예측 + 25.6]`이었는데,
   검증셋에서 실제 RUL은 예측보다 "최대 25.6 작고 최대 18.6 큰" 분포였으므로 방향이 반대였습니다.
   고장이 더 빨리 올 수 있는 **위험 쪽 폭을 작게** 보여주고 있었습니다.
2. **생존곡선이 모델 예측을 반영하지 않았음.** 엔진의 현재 나이(누적 사이클)만 보고 train 엔진 수명
   분포로 그렸기 때문에, 예측 RUL 15.6인 #37에 "앞으로 40사이클 더 버틸 확률 84%"가 함께 표시되는
   모순이 있었습니다.

**바뀐 계산 방식**: 검증 엔진(학습에 안 쓴 20대)에서 모델이 **비슷한 값(±10 cycle)을 예측했던 순간들**을
모아, 그때 실제로 남아 있던 RUL 분포를 봅니다.
- 90% 구간 = 그 분포의 5%~95%
- 생존곡선 S(x) = 그중 실제 RUL이 x보다 컸던 비율 ("앞으로 x 사이클 더 가동해도 아직 고장나지 않을 확률")
- 음영 = 검증 엔진을 엔진 단위로 다시 뽑는 부트스트랩(1000회) 90% 구간

세 값이 모두 같은 근거에서 나오므로, 이제 예측 RUL 기준선이 생존곡선의 50% 근처를 지나갑니다.

| 엔진 | 예측 RUL | 예전 구간 | 바뀐 90% 구간 |
|---|---|---|---|
| #37 | 15.6 → 15.2 | 0.0 – 41.2 | 2.0 – 29.0 |
| #43 | 61.6 → 60.1 | 43.0 – 87.2 | 40.0 – 81.0 |
| #47 | 125.0 | 106.4 – 125 | 97.0 – 222.0 |

(예측 RUL이 조금 바뀐 것은 2026-09-29에 파이프라인을 처음부터 다시 실행하면서 LSTM을 재학습했기
때문입니다 — torch 버전 차이로 소수점 수준 차이, test MAE 10.84 → 10.85.)

#47처럼 예측이 상한(125)에 붙은 엔진은 "적어도 한참 남았다"는 뜻이라 위쪽 구간이 넓게 나옵니다

## 11. 위험 기준을 20 → 30으로 통일 (2026-09-29)

과제 문서(주제 F)의 필수 과제는 "잔여 사이클이 임계값(예: 30) 이하인 구간을 위험으로 정의한 이진 분류"이고,
팀 문제정의서도 위험 기준을 30으로 적었습니다. 그런데 대시보드 빨간불은 20 미만이라 발표에서 두 기준이
섞일 수 있어 **빨간불을 30 이하로 통일**했습니다.

- 기준값은 이제 `mock.ts`의 `riskThresholds`(분석 레포 `common.py`의 `DANGER_RUL`)에서 읽습니다. 화면 문구의
  "20 cycle"처럼 숫자를 직접 적은 곳을 모두 이 값으로 바꿔서, 기준을 다시 바꿔도 화면 코드를 고칠 필요가 없습니다.
- 기준이 바뀌면서 예전 주의 엔진(#56, #18)이 위험으로 넘어가, 주의 2대를 위험 경계에 가장 가까운 #91·#62로 다시 골랐습니다.
- 조기경보 성능·비용 시뮬레이션 숫자도 새 기준으로 다시 계산됐습니다 (§4, §6).

## 12. FD004로 전환 + 위험 기준 40으로 통일 (2026-09-30)

팀의 주 데이터가 FD001(운전조건 1종·고장모드 1종)에서 **FD004(운전조건 6종·고장모드 2종)**로 바뀌어, 대시보드도
FD004 결과를 보여주도록 바꿨습니다.

**위험 기준 30 → 40.** 과제 예시값(30) 대신, C-MAPSS 정비 일정 논문(de Pater et al. 2022, Lee & Mitici 2023)의 운영 조건
(정비 준비 7일, 정비 슬롯 10~20일 간격, 주간 계획)으로 "예측 RUL이 N 이하면 정비"를 시뮬레이션해 정비 비용이 가장 낮은
N = 40을 골랐습니다. 30이면 정비 준비가 끝나기 전에 엔진 8대 중 1대꼴로 고장 납니다. 과제 분류 라벨·대시보드 빨간불·
정비 경보가 모두 이 값 하나(`riskThresholds`)를 씁니다. 주의 구간 상한은 같은 규칙(위험 기준의 2배)으로 80.

**바뀐 화면**
- 데이터셋 이름·설명·test 엔진 수를 `mock.ts`의 `dataMeta`에서 읽도록 바꿈 (홈 제목, 시나리오 문구). 데이터셋을 바꿔도 화면 코드를 고칠 필요가 없음.
- 센서 추이: 센서가 데이터셋마다 달라서(FD004 상위 3개: s3 고압압축기 출구 온도, s17 블리드 엔탈피, s8 팬 속도) 이름·단위·축 범위를
  `trendMeta`에서 읽음. 값은 비행 조건 차이를 뺀 운전조건 보정값(원래값 − 조건 평균 + 전체 평균, 단위 유지).
- 보여줄 엔진 9대와 대표 엔진을 사람이 고르지 않고 규칙으로 자동 선정 — 위험 5대(대표 엔진 + 예측 RUL 최저 4대), 주의 2대(위험 경계에 가장 가까운),
  정상 2대(가장 낮은 1대 + 가장 여유 있는 1대). 대표 엔진은 마지막 25사이클 안에 정상→주의→위험 교차가 모두 보이는 위험 엔진 중 예측이 가장 크게
  떨어지는 엔진: **#187**. 선택 결과: #58, #158, #31, #155, #187 (위험) / #197, #77 (주의) / #199, #246 (정상).

**바뀐 숫자** (test 248대, 엔진별 마지막 관측 시점, LSTM 예측 RUL ≤ 40)
- 위험 조기경보: 실제 위험 69대 중 탐지 60 / 누락 9 / 오탐 6 → precision 0.909 / recall 0.870 / F1 0.889
- 비용 시뮬레이션의 탐지·누락·오탐 건수도 위 값으로 바뀜 (금액 가정값은 그대로).
