# Sentinel 시연 영상 시나리오 (3분 이내, 재설계)

> 한 줄 메시지: **"예측을 결정으로 — 기한 안에, 규칙 안에, 사람이 승인하고, 돈으로 증명한다."**
> 다른 팀도 남은 수명을 예측한다. 우리 영상은 예측 정확도가 아니라 **예측 다음에 무엇이 바뀌는가**를 보여 준다.

### 검토하다 발견한 제품 문제 (촬영 전에 고치는 것을 권함)
1. **결재 요청 창의 추천 날짜에 가동 한계일 뒤의 날짜가 섞여 나온다.** #32는 가동 한계가 11/01인데 추천 날짜에 11/2·11/3·11/4가 같이 뜬다. 상세 화면 상단의 "추천 정비 기간"은 한계일 전 날짜만 보여 줘서 두 화면이 서로 다르다. 결재 장면에서 화면에 그대로 보인다.
2. **고장 진단 탭 "시스템이 알린 시점" 그래프에서 "주의 시작"과 "위험 시작" 글자가 겹친다.** 두 시점이 가까울 때 생긴다. 영상에서 이 그래프를 보여 주므로 눈에 띈다.
3. (판단 필요) **알림 민감도 기본값 '비용 최우선'의 위험 엔진 포착률이 88%다.** 위험 엔진 10대 중 1대 남짓을 놓친다는 뜻이다. 영상에서 민감도 화면을 보여 주면 "기본값이 왜 놓치는 쪽이냐"는 질문이 나올 수 있다. 기본값을 '균형'(96%, 오경보 1.7%)으로 바꿀지 정해야 한다.

## 2. 주인공 엔진: Engine #32

| 항목 | 값 (처음 상태 기준, 날짜는 촬영일에 따라 바뀜) |

## 3. 화면 구성 (1920×1080)

- **좌: PC 1440×1080 = 정비 담당자(김정비)** / **우: 폰 480×1080 = 운영 책임자(박운영)**. 같은 브라우저 컨텍스트의 페이지 두 개를 동시에 녹화해 가로로 붙이면 정확히 1920×1080이 된다.
- 영상 전체를 이 분할로 간다. 폰 쪽은 평소엔 책임자 현황을 띄워 두고, 결재 장면에서 주인공이 된다. (장면마다 화면 폭이 바뀌지 않아 편집이 단순하고, "두 사람이 같은 시스템을 동시에 쓴다"가 계속 보인다.)
- 제목 카드와 엔딩 카드만 1920 전체를 쓴다.
- 커서: Playwright 녹화 도구의 cursor 옵션만 사용. `present=0`. 동작 사이 2~3초.
- Slack 컷: 결재 직후 실제 #결재-알림 채널 캡처를 3초 삽입(촬영 후 채널을 캡처해 넣는다).

## 5. 예상 질문과 답

| 질문 | 답 |
|---|---|
| 기한이 이미 지난 엔진은 어떻게 하나? | 결재 요청에 "가동 한계일 뒤 일정"이 표시되고, 책임자가 승인할 때는 **긴급 예외 승인**으로 바뀌어 사유가 필수다. 이력에 [긴급 예외]로 남는다. |
| 예측 오차는? | 시험 엔진 248대 기준 평균 절대오차 약 17 cycle(약 6일), RMSE 약 25 cycle. 그래서 날짜 하나가 아니라 90% 구간과 정비 준비 기간을 함께 쓴다. |
| 30% 절감은 믿을 만한가? | 경보 구간 115대를 실제 남은 수명으로 사후 검증한 시뮬레이션이다. 안전 여유 최적값을 같은 데이터에서 골랐으므로 실제로는 이보다 작을 수 있다. 정기 정비도 가장 유리한 주기를 미리 안다고 가정해 유리하게 계산했다. 단가는 공개 자료 기반 가정값이고 설정에서 바꿀 수 있다. |
| 기본 민감도에서 위험 엔진 12%를 놓치지 않나? | 과거 검증 데이터 기준 포착률 88%, 오경보 0.6%다. '균형'으로 올리면 96%·1.7%. 놓침과 불필요한 점검 사이의 선택이라 화면에서 근거를 같이 보여 주고 사람이 고르게 했다. (기본값을 바꾸면 이 답도 바뀐다.) |
| 처음 화면에 기한 지난 엔진이 왜 이렇게 많나? | 도입 첫날 시점의 상황을 가정했다. 그동안 관리되지 않던 위험 엔진이 한꺼번에 드러난 상태다. |
| 챗봇이 틀린 숫자를 말하면? | 챗봇은 일정·엔진 조회 같은 시스템 도구만 호출할 수 있고, 답 아래 '근거 보기'로 어떤 도구를 어떤 조건으로 불렀는지 보여 준다. 일정 변경·승인은 할 수 없다(읽기 전용). |
| 지도의 비행기는 실제 운항인가? | 아니다. 색의 비율과 올렸을 때 나오는 엔진 값만 실제 데이터이고, 노선과 위치는 표시용이다. |

## 6. 촬영 전 체크

1. 위 "제품 문제" 1·2를 고치고(3은 결정), 배포 후 `npm run demo:check`.
2. 녹화 시작 주소: 담당자 페이지 `…/?demo=reset&present=0`(로그인부터), 책임자 페이지 `…/?as=manager&present=0`(초기화하지 않음).
3. 한 번 리허설로 3D·로딩을 데워 두고, 다시 `demo=reset` 후 본 녹화.
4. 녹화 뒤 Slack #결재-알림 채널을 캡처해 1:27 컷에 넣는다(워크스페이스 이름·다른 채널이 안 보이게 메시지 부분만).
5. 녹화할 때마다 실제 Slack 채널로 알림이 간다. 리허설 횟수만큼 메시지가 쌓인다.
